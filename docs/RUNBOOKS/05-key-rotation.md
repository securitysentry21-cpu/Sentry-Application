# Runbook 05: Key rotation

> Nothing here has been tried on the test environment. Secrets live in AWS Secrets Manager, generated by Terraform (`secrets.tf`). Tasks read their secrets **only when they start**, so every change below also needs a redeploy (G01). Never print, paste or commit a secret. Setup: `docs/RUNBOOKS/README.md` › Before you start.
> No rotation schedule exists in the specs (SEC §13 asks only for documented procedures). Rotate on suspicion, on a staff change, or when the owner sets a schedule.

## When to use

A secret, key or database password may have leaked; a person with access left; a provider asks for a new key; or the owner schedules a rotation. There is no alarm for this.

## First five minutes

1. Which secret, and why? A leak is urgent. A schedule is not.
2. Pick a quiet hour and tell people (Tell). Have the previous release commit at hand.
3. See what a change would do before applying it.

```bash
infra/scripts/tf.sh <env> plan -replace=<address>
```

## Decide

| If                               | Do                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| One label leaked or was damaged  | Rotate that checkpoint only: dashboard › Sites › "New QR label" (`POST /checkpoints/:id/rotate-qr`). The old label stops at once. No secret change. |
| QR secret, Cognito secret leaked | Its section below.                                                                                                                                  |
| VAPID private key leaked         | VAPID section, now: an attacker could send fake alarms to subscribed browsers.                                                                      |
| Firebase key leaked              | Revoke the key in Firebase first, then the Firebase section.                                                                                        |
| Database URL or password leaked  | Database section, then read the audit log (runbook 08).                                                                                             |

## QR token secret

What the code does (`apps/api/src/routes/sites.ts`, `auth/codes.ts`):

- A scan is looked up by the **stored hash** of the token. The secret is not used when scanning. So after the secret changes, labels already stuck on walls **keep working**.
- The secret is used to create a checkpoint (version 1), to build the **print sheet**, and by **rotate-qr**. After the change, a sheet printed for an existing checkpoint carries a token whose hash is not in the database: **a label printed after the change will not scan** (`INVALID_QR`).
- Rotating a checkpoint writes the hash of the new-secret token and raises its version, so print-after-rotate is correct. The old label then stops, and shows plain "unknown" rather than "Old QR code", because its retired hash was worked out with the new secret.
- `docs/ARCHITECTURE.md §11.1` says a rotation "requires reprinting all labels". In the code it is the other way round: old labels keep working until each checkpoint is rotated.

Steps:

1. Change the secret [never tried]:

```bash
infra/scripts/tf.sh <env> apply -auto-approve -replace=random_password.qr_token_secret
```

2. Redeploy `api` and `worker` (runbook 01, Fix 1, for each; G01).
3. **Do not print yet.** For every checkpoint of every organization: dashboard › Sites › "New QR label". Then print the sheet and stick the labels. There is no bulk action. [GAP: no "rotate all checkpoints" command (G14). By hand, one checkpoint at a time, by each company's administrator.]
4. Until a checkpoint has a new label stuck up, its scans fail with `INVALID_QR` and patrol rounds show it missed.

## VAPID (dashboard push)

1. Apply. The API task definition changes (it carries the public key), so `api` redeploys by itself. Redeploy `worker` too (G01).

```bash
infra/scripts/tf.sh <env> apply -auto-approve -replace=tls_private_key.vapid
```

2. Every duty officer must open Settings › Notifications and enable notifications again; the page replaces a subscription made with another key (`apps/web/lib/push.ts`). Until then their pushes fail (expected `HTTP_401` or `HTTP_403`, runbook 02). The dashboard alarm is unaffected.

## Firebase service account

1. In the Firebase console create a new key for the service account. Put its JSON into `local.auto.tfvars` as `fcm_service_account = <<EOT ... EOT`.
2. `infra/scripts/tf.sh <env> apply -auto-approve`, then redeploy `worker`.
3. Check the worker log shows no `FCM_AUTH` failures, then delete the old key in the Firebase console. Not applicable yet: the Firebase project does not exist (EXT-09).

## Cognito client secret [untested]

1. `infra/scripts/tf.sh <env> apply -auto-approve -replace=aws_cognito_user_pool_client.dashboard` creates a new client with a new ID and secret. The task definitions change with the new ID, so `api` and `worker` redeploy. Redeploy them once more afterwards (G01), in case a task started before the new secret was written.
2. Test a sign-in. Existing dashboard sessions are our own cookies and stay valid.
3. **Never replace the user pool.** People's accounts would get new identities and the sign-in code does not re-link an account that already has one (`routes/auth.ts`). [GAP: user-pool loss is unrecoverable without a code change (G11).]

## Database role passwords [untested]

Order matters: a service that starts before the database knows the new password cannot connect.

1. New password into the secrets (services keep running on their open connections):

```bash
infra/scripts/tf.sh <env> apply -auto-approve -replace='random_password.db["app_runtime"]'
```

2. Make the database accept it: re-run the migration task for the current commit (it re-sets all four passwords; `deploy-db.ts`). Use the commit in `infra/terraform/env/<env>.release.tfvars`:

```bash
infra/scripts/release.sh <env> <current commit>
```

3. At once redeploy `api` and `worker` (G01). The window between steps 2 and 3 is minutes: new connections from old tasks fail.
4. Repeat for `system_worker` and `retention_worker` (the worker). `migrator` is used only by step 2.

## End sessions

| Scope                                               | What exists                                                                                                                  |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| One phone                                           | Guards page › revoke device (`POST /devices/:id/revoke`, Owner or Administrator). Its sessions end at once.                  |
| One guard                                           | Terminate (sessions end, phone retired, shifts ended) or Suspend (refused on the next request).                              |
| One dashboard member                                | Members page › disable. Refused on the next request; their live stream closes within about a minute.                         |
| Everyone in an organization, or all dashboard users | [GAP: no tool. The only switch is `organizations.status = 'SUSPENDED'`, which has no command either (runbook 08, G15, G23).] |
| One dashboard user in every organization            | [GAP: no operator command to disable a user (G15).]                                                                          |

## Confirm it is fixed

- Services stable, `infra/scripts/smoke.sh <env>` passes, the worker log shows `worker heartbeat` and no new provider or database errors.
- QR: a new label scans; an old label of a rotated checkpoint says unknown or "Old QR code". VAPID: a test alert arrives after re-subscribing. Passwords: `/api/v1/ready` answers 200 and the worker keeps logging `worker heartbeat`.

## Afterwards

Record date, secret, reason, who did it. Delete any temporary copy of a key. If a leak was real, check CloudTrail and the audit logs (runbook 08).
